```rust
//! The one way `ws` writes a shared file.
//!
//! Temp + rename, with a per-process temp name. The fixed-temp-name variant of
//! this code has been written and fixed five separate times in this codebase,
//! each time in a module modeled on a previously-fixed one: a shared `*.tmp`
//! path lets two live `ws` processes interleave their writes before either
//! renames, and the rename being atomic does not save you. Every writer goes
//! through here so the unsafe shape has nowhere left to be reintroduced.
//!
//! This handles the *write*. Refusing to overwrite a file that failed to parse
//! is the caller's job, because only the caller knows the format.
use anyhow::{Context, Result};
use std::path::Path;

pub fn atomic_write(path: &Path, contents: impl AsRef<[u8]>) -> Result<()> {
    if let Some(dir) = path.parent() {
        std::fs::create_dir_all(dir)
            .with_context(|| format!("failed to create {}", dir.display()))?;
    }
    let ext = match path.extension().and_then(|e| e.to_str()) {
        Some(e) => format!("{e}.tmp.{}", std::process::id()),
        None => format!("tmp.{}", std::process::id()),
    };
    let tmp = path.with_extension(ext);

    if let Err(e) = std::fs::write(&tmp, contents) {
        let _ = std::fs::remove_file(&tmp);
        return Err(e).with_context(|| format!("failed to write {}", tmp.display()));
    }
    if let Err(e) = std::fs::rename(&tmp, path) {
        let _ = std::fs::remove_file(&tmp);
        return Err(e).with_context(|| format!("failed to rename into {}", path.display()));
    }
    Ok(())
}
```

### Task 6: The read-error-clobber family

Added mid-phase. Task 3's review found two live instances of this shape while reading adjacent code, and a
survey then found a third. It is the same family already fixed three times (`meta::update`,
`registry::load`, `context::regenerate_with_handoff`), and it is the second recurring bug class in this
codebase. Task 3 ended the temp-name family by making the safe path the only path; this task ends this one
the same way, by naming the shape, enumerating every instance, and proving none remain.

**The shape:** a read whose *error* is mapped to a default or empty value, followed by a write-back of that
value. Absent is a legitimate default. Unreadable is not: a permission error, an I/O error, or a partial
read then silently destroys the real contents on the next write.

**The discriminator that decides whether an instance is a defect:** does a write-back follow? A lenient read
whose value is only displayed is fine and must be left alone. A lenient read whose value is written back is
data loss. Judge each site on that question, and say so per site in your report.

**Known instances (verify each, and find any the survey missed):**

| Site | What is lost |
|---|---|
| `src/secrets.rs` `FileStore::load` — `Err(_) => return Ok(BTreeMap::new())` | **Credentials.** A transient read error then `ws -secrets set` writes a store containing only the new secret over every existing one. |
| `src/hooksetup.rs:150-153` — backup read `.ok().and_then(…).unwrap_or_default()` | The user's only record of their original statusline command, which the backup exists to preserve. |
| `src/config.rs:98` — `Err(_) => Config::default()` in `set` | The whole config. Already refuses an *unparseable* file; a read *error* still defaults and writes back. |
| `src/internal.rs:381-383` — note manifest | Judge it: does a write-back follow? |
| `src/lock.rs:38` — `read_pid` maps a read error to `None` | Not a write-back, but an unreadable lock reads as *stale* and gets reclaimed while a live process holds it. Judge whether to fix or document. |

**Files:**
- Modify: `src/secrets.rs`, `src/hooksetup.rs`, `src/config.rs`, and any further instance you confirm
- Test: alongside each fix

**Interfaces:** no new public API. Each fix is the same edit: match on `ErrorKind::NotFound` for the
